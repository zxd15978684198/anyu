## 1. 为什么做

现状（读码实测，`app/services/embedding.py` 350 行）：

- 只有两种形态：云端 OpenAI 兼容 HTTP、以及 SHA-256 确定性兜底（无语义，注释已自认「不能作为召回质量证据」）。
- 云端不可用时**没有第二次机会**：`build_embedding_provider()` 只在启动时二选一，运行期无重试、无主备切换。
- 召回拿不到向量直接 `return []`，且唯一上界是 `EMBEDDING_TIMEOUT_MS=5000`；而语音链路端到端预算 P95 ≤1.5s，一次卡住就爆预算。

本机约束（实测）：物理内存 7.8 GB（HP OMEN 15-dc），Docker VM 3.7 GB，已跑 9 个容器；bge-m3 fp32 常驻约 3 GB，常驻必 OOM（内核 OOM killer 会随机杀进程，不报错、极难查）。

## 2. 方案

选 **C：int8 量化 + 按需容器**。

- 模型：`Xenova/bge-m3` 的 `onnx/model_quantized.onnx`（int8 动态量化，约 570 MB）。
- 服务：仓库自建 `deploy/embedding/`，只暴露 OpenAI 兼容 `POST /v1/embeddings` 与 `GET /health`。
- 组合：`docker compose --profile embedding up -d embedding`，`mem_limit: 1536m`，端口 `127.0.0.1:7004`。
- 后端零代码改动：把 `EMBEDDING_BASE_URL / EMBEDDING_MODEL / EMBEDDING_API_KEY` 指向它即可。

三条写死、不允许漂移的口径：

1. **同一模型、同一 1024 维**：换模型 = 向量空间不一致 = 召回静默劣化（不报错）。
2. **CLS pooling + L2 归一化**：BGE-M3 官方 dense 表征就是 `last_hidden_state[:, 0]` 归一化；用 mean pooling 会与云端向量不可比。
3. **不常驻**：与 funasr / voiceprint 抢内存；演示前起、演示后关。

## 4. 分步

1. 写服务与镜像 → `docker compose --profile embedding build`
2. 拉模型 → `python deploy/embedding/fetch_model.py`
3. 起容器 → `docker compose --profile embedding up -d embedding`；`curl /health`
4. 真打一次 `/v1/embeddings`，核对 1024 维
5. 后端指向它，跑 `tests/test_memory_service.py`（需 PG/Redis）
6. 关容器，确认主栈不受影响

## 5. 验收

- `/health` 返回 200 且 `ready=true`；`/v1/embeddings` 返回 `data[].embedding` 长度 1024
- 同一句两次结果一致；不同句余弦 <0.9
- `ruff check .` 通过；`pytest tests/test_embedding_server.py` 通过
- `docker stats` 峰值 RSS ≤1.5 GB
- 停掉容器后后端回落确定性兜底（日志 `embedding_provider_degraded`），主栈不崩

## 6. 回滚

删 `docker-compose.yml` 的 `embedding` 服务块 + `deploy/embedding/` + `embedding-model/`；`.env` 清空三项即回到确定性兜底。
