# 环境与排障（Anyu）

> 本文件承接 README 里「只有在本机才会遇到」的内容：工具链坑、无 `uv` 机器的容器兜底、nginx 片段自检。
> 主线说明仍在 [`README.md`](../README.md)；本文件不含任何本机绝对路径。

## 1. 本机开发环境已知坑

| 现象 | 根因 | 规避 |
| --- | --- | --- |
| 仓库根冒出 `pytest-of-<用户名>/` | `TEMP` 是 8.3 短名（形如 `<用户名>~1`），`tempfile.gettempdir()` 校验失败后回退到 CWD，pytest 的 tmp 工厂于是落在仓库根 | 已加 `.gitignore`；彻底规避可给 pytest 传 `--basetemp` 指向长路径目录 |
| 往用户目录写报 `WinError 5`（`%LOCALAPPDATA%\Temp`、`~/.cache`） | 进程运行在只放开工作区的受限环境里 | 临时产物一律写仓库内已被忽略的目录（如 `spikes/**/out/`、`.tmp/`） |
| `uv run alembic` 报 `UnicodeDecodeError: 'gbk' codec can't decode byte 0x89` | configparser 用平台 locale 读 `alembic.ini` | **`alembic.ini` 必须 ASCII-only**，注释里不许出现中文 / 全角字符 |
| 容器内 edge-tts 转码报 `TTSUnavailable("ffmpeg not found")` | `python:3.12-slim` 不带 ffmpeg | 设计内行为：生产走云端 TTS，edge 只是宿主机兜底；容器里相关用例自动 skip |
| 容器在两次命令之间被回收（`docker ps -a` 显示 `Exited (0)`） | 部分托管环境在调用结束后回收容器 | 「起库 → 另开一次命令跑测试」必然失败；改成**库与测试同一个容器、一次命令跑完** |
| `docker run ... bash -s <<'SH'` 返回空输出 | heredoc 经某些终端/编排工具传递时被吞 | 先把脚本落成文件（`/tmp/x.sh`），再 `-v /tmp/x.sh:/v.sh:ro` 挂进容器执行 |
| `uv run` 报 `Failed to initialize cache at ...：拒绝访问 (os error 5)` | uv 缓存目录不可写（权限或只读盘） | 腾出可写缓存目录，或直接用项目 `.venv` 里的解释器跑：`./.venv/Scripts/python.exe -m pytest -q` |

## 2. 没有 `uv` 的机器（容器兜底）

**没有 `uv` 的机器**（WSL 等环境：`.venv` 与系统 `python` 都没有 `pip`）：上面的 `uv sync` 起不动，改用容器跑同一批命令。

```bash
docker run -d --name anyu-verify -v "$PWD":/w -w /w python:3.12-slim sleep infinity
docker exec anyu-verify pip install fastapi "uvicorn[standard]" pydantic-settings \
  sqlalchemy alembic "psycopg[binary]" pytest pytest-asyncio httpx ruff
docker exec -w /w anyu-verify sh -c 'PYTHONPATH=/w python -m pytest -q'
docker exec -w /w anyu-verify sh -c 'PYTHONPATH=/w exec uvicorn app.main:app --port 8000'
```

需要连 PostgreSQL 跑迁移的完整版本（含建库、`alembic upgrade head`、起服务验证接口）见 [`AGENTS.md` §3.1](../AGENTS.md)。

## 3. nginx 配置片段自检

一次性验证 nginx 片段（无需常驻服务，Docker 在 WSL 里即可）：

```bash
wsl -e sh -lc "docker run --rm -v \"$PWD/deploy/nginx.conf\":/etc/nginx/conf.d/default.conf:ro nginx:alpine nginx -t"
```

> 片段改动后跑一次即可，不需要常驻服务。

## 4. 本地量化向量服务（bge-m3 int8）

云端 embedding 不可用时，代码只有「确定性兜底」（SHA-256 哈希噪声，无语义，不能当召回质量证据）。
想在本地开发或断网演示时用**真向量**，起 `deploy/embedding/` 那个服务：

```bash
# ① 拉权重到 ./embedding-model（约 570 MB，只拉一次；默认走 hf-mirror.com）
python deploy/embedding/fetch_model.py

# ② 起服务（只绑 127.0.0.1:7004，默认不参与 `docker compose up`）
docker compose --profile embedding up -d embedding

# ③ ready=true 才算就绪（加载期 /health 返回 503）
curl -s localhost:7004/health
```

`.env` 改三行（模板见 `.env.example` 的 Embedding 段）：

```bash
EMBEDDING_BASE_URL=http://embedding:7004/v1
EMBEDDING_MODEL=bge-m3
EMBEDDING_API_KEY=local
```

> `EMBEDDING_API_KEY` 必须非空——后端只有「URL / MODEL / API_KEY 三项齐全」才会走 HTTP，
> 否则启动时就退化成确定性兜底。本服务只在自身也设了同名变量时才真校验 Bearer。

演示完**一定要关**：`docker compose --profile embedding stop embedding`。

| 坑 | 说明 |
| --- | --- |
| 内存 | Docker VM 只有 3.7 GiB，int8 常驻约 1 GiB（`mem_limit: 1536m`）。**它和 `funasr` / `voiceprint` 同时跑必不够**，起它前先停那两个：`docker compose stop funasr voiceprint` |
| 维度 | 固定 1024。换模型必须先确认新模型维度；维度不符后端按 `bad_dimension` 拒收，更糟的是维度相同但向量空间不同的模型——召回静默变差，不报错 |
| 池化 | 默认 CLS（BGE-M3 官方 dense 口径）。改成 `EMBEDDING_POOLING=mean` 后与云端向量不可比，别混用 |
| 下载 | `fetch_model.py` 默认端点 `hf-mirror.com`，但该站对大文件会 302 到 `cas-bridge.xethub.hf.co`，实测只有 **~15 kB/s**（570 MB 要十几小时）。大陆推荐直接走 ModelScope（同一份权重、尺寸完全一致），见下方命令 |
| 权重 | `./embedding-model/` 已进 `.gitignore`（570 MB，不入库）；换目录用 `EMBEDDING_WEIGHTS_DIR` |

大陆拉权重（ModelScope 镜像，实测单连接 ~480 kB/s）：

```bash
BASE=https://www.modelscope.cn/models/Xenova/bge-m3/resolve/master
mkdir -p embedding-model/onnx
curl -L -o embedding-model/tokenizer.json "$BASE/tokenizer.json"
curl -L -o embedding-model/onnx/model_quantized.onnx "$BASE/onnx/model_quantized.onnx"
# 校验尺寸：tokenizer.json = 17,082,821；model_quantized.onnx = 569,694,530
```

> 单连接慢时可把 onnx 切成 6 片并行 `curl -r` 再 `cat` 合并（实测聚合 ~1.5 MB/s，约 6 分钟）。
